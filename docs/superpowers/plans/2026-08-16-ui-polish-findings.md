# TerraWatch UI Polish: Research Findings (Color, Detail Sheet, Motion)

**Type:** Research only — no app code changed. Companion to `docs/superpowers/plans/2026-08-15-terrawatch-plan-5-polish.md`.
**Source:** user dogfooding feedback 2026-08-15/16 — "check the color schemes," "detail bottomsheet extra dismiss button and whatsapp share button feels weird," "add animations."
**Branch:** `feat/plan-5-polish`. **Method:** direct code read (Tokens.kt/TerraTheme.kt/DetailSheet.kt/etc.), direct read of 6 real device screenshots from `docs/qa/plan-5-device-matrix/`, a Python/Pillow script computing real WCAG 2.x contrast ratios from the actual token hexes and pixel-sampling the actual screenshot PNGs, and — where `m3.material.io` itself turned out to be an unfetchable JS SPA (see Sources) — direct extraction of the **actual resolved Compose Multiplatform Material3 1.8.2 / animation-core 1.9.0 dependency source** from this machine's Gradle cache, which is a strictly better source than the marketing site for a Compose-specific question anyway.

---

## Executive Summary

- **Magnitude badges — the app's own "single most important glanceable fact" — fail WCAG contrast for the two most common bands.** White text on `MagLow` is 2.45:1 and on `MagModerate` is 2.04:1 (both need ≥3:1 even as large bold text); together LOW+MODERATE are 92% of all quakes in the sampled Insights data (663+186 of 920).
- **An unbranded Material 3 default color is leaking through the whole app.** `#4A4458` (dark)/`#E8DEF8` (light) — M3's stock `secondaryContainer` baseline — appears on every selected filter chip, the Settings sliders' inactive track, and the bottom-nav selected-tab pill, because `TerraTheme.kt` never defines that role. Confirmed three independent ways: code (zero overrides anywhere), the actual Material3 1.8.2 dependency source, and exact-match pixel sampling of real screenshots.
- **The detail sheet's "Dismiss" button is a proven, provable accessibility-redundant 4th dismiss path** — the real M3 `ModalBottomSheet` source (this project's actual dependency) shows the drag handle already carries a genuine, TalkBack-actionable `dismiss()` semantics action, and the scrim already carries its own `contentDescription` + `onClick`. Removing the custom button costs nothing accessibility-wise, and it is visually a dead ringer for the WhatsApp quick-share button next to it (identical `OutlinedButton` styling) — very likely the actual source of "feels weird."
- **DetailSheet's content `Column` has no scroll modifier at all.** A real device screenshot shows a content-heavy sheet (tsunami banner + felt row + news section) already overflowing past the bottom of a real 2400px screen while the sheet is fully expanded — this is a reachability bug, not just a layout-taste question.
- **The app's three "signature" springs all use `Spring.DampingRatioMediumBouncy` (0.5)** — the second-bounciest of Compose's four built-in presets, confirmed via the actual `animation-core` source — sitting in direct tension with the "calm brand, nothing playful about severity" constraint.

## Part 1 — Color Scheme Research + Audit

### Research: what the industry does now (2025–2026)

- **Material 3 Expressive (May 2025)** pushes color from decoration toward *communication*: "color has a much deeper role than just visual appeal… bright and bold tones draw attention to actions, while subtle shades support less urgent areas" — clearer separation between primary/secondary/tertiary roles specifically so users can tell "which actions matter the most." Directly relevant to TerraWatch's own accent discipline question (Part 1 table below).
- **Material dark-theme guidance** (both the M2 dark-theme page and the M3 tonal-surface model, via search) is consistent on two points: (1) dark surfaces should get **lighter**, not blacker, as elevation increases — "a black shadow on a dark background is visually not perceptible" — and (2) "a dark theme should avoid using saturated colors, as they don't pass WCAG's accessibility standard of at least 4.5:1 for body text against dark surfaces." TerraWatch's Dusk scheme is a good but *minimal* version of this — `DuskCanvas`→`DuskCard`→`DuskCardVariant` is only 2.5 steps of lightness, relying on Material's `tonalElevation` blend for the rest (see Part 1 table).
- **Calm dashboard apps** (Overdrop, and weather-app design coverage generally): dark-first UI, but color is *earned* — "adaptive color palettes that reflect different weather types," not decorative accenting. This matches Calm Guardian's own "severity color only, no brand color elsewhere" instinct — the finding below is that TerraWatch doesn't fully control where its *non*-severity accent color comes from (see the `secondaryContainer` finding).
- **Dark-map conventions** (Google Maps Night Mode / general dark-map coverage): "dark style maps are designed to minimize user distraction, with everything as dim as possible and just enough contrast to make the map readable" — night mode exists specifically so map chrome doesn't fight the content drawn on top of it (pins, rings). TerraWatch's map pins already carry their own fixed semantic colors (`magnitudeColor`) independent of map style, which is the right call per this convention — the map's own base style/tiles were out of scope for this pass (not audited here; flagged as a gap).
- **Calm-design mandate** (UXmatters, fetched in full — see Sources and Part 3): "reduce cognitive overload through deliberate visual choices… when everything competes for attention — by using bold fonts or clashing colors — users must work harder to interpret screens." Directly supports treating the `secondaryContainer` leak as a real finding, not a nitpick: an un-chosen purple competing against the chosen Ink/Water/Land palette is exactly this kind of unintentional competition.

### Diagnosis

**The user's complaint has two distinct, provable causes, not one vague one:**

1. **"Extra dismiss button" is an accessibility-redundancy fact, not a taste call.** Per Material's own component docs (`material-components-android/docs/components/BottomSheet.md`, fetched): a modal sheet's standard dismiss set is *scrim tap + swipe-down + (for accessibility) the drag handle* — "to support dragging bottom sheets with accessibility services such as TalkBack, Voice Access, Switch Access, etc." Reading the **actual** `ModalBottomSheet.kt` source from this project's real dependency (`org.jetbrains.compose.material3:material3:1.8.2`) confirms both of TerraWatch's *implicit*, already-present affordances are fully wired for TalkBack today, with zero custom code:
   - The drag-handle wrapper: `Modifier.semantics(mergeDescendants = true) { … dismiss(dismissActionLabel) { animateToDismiss(); true } … }` — a real, named, focusable `dismiss` accessibility action.
   - The scrim: `Modifier.semantics(mergeDescendants = true) { contentDescription = closeSheet; onClick { onDismissRequest(); true } }` — a second, independent, focusable close action.

   So DetailSheet's custom `OutlinedButton("Dismiss")` is a **fourth** dismiss path, and — critically — **removing it does not regress accessibility at all**, since the other two are library-guaranteed, not app code TerraWatch would be giving up.

2. **The WhatsApp button and the Dismiss button are visually identical**, confirmed directly in `docs/qa/plan-5-device-matrix/task3-detail-open-no-ad.png`: both render as same-size, same-corner-radius `OutlinedButton`s, one row apart. A user skimming sees two look-alike pills where only one closes anything — a real visual-hierarchy failure. This is compounded by the fact that the *actual* primary action, **Share** (the filled button), is nearly invisible in dark theme (row 7 of the Part 1 table, **1.00:1** contrast against its own sheet background) — so in practice the user sees "two identical outlined pills, plus one that barely renders," which is a coherent, concrete explanation for "feels weird" beyond a vague hunch.

3. **A separate, higher-severity bug found in passing:** `DetailSheet.kt`'s content `Column` has **no** `Modifier.verticalScroll(...)` and is not a `LazyColumn` (confirmed: `grep -rn "verticalScroll|LazyColumn" DetailSheet.kt` → zero matches). `docs/qa/plan-5-device-matrix/store/detail-sheet-clean-news-error-state.png` shows a real capture where the sheet is already at/near full expansion and its own content (tsunami banner + felt row + news-error row) reaches the literal bottom edge of a 2400px screen with nothing left to show — meaning on a shorter device, or any quake with a *few* more populated fields (e.g. a real "3 headlines" news card instead of the error state pictured), Share/Dismiss/quick-share can become **physically unreachable**, by touch or by TalkBack linear navigation, with no way to scroll to them. This is a reachability defect independent of the redundant-button question.

### Share-row convention research

Industry convention (Android's own Sharesheet mechanism, plus general share-icon coverage found via search) is a **single share affordance that defers to the OS system chooser**, which itself ranks and renders installed-app icons/branding automatically — zero per-target app maintenance, and it scales to however many share-capable apps are actually installed instead of a fixed hardcoded 3. Hardcoding specific third-party packages (as TerraWatch's `ShareTarget.WHATSAPP/X/THREADS` enum does) is the less-common pattern industry-wide, typically reserved for very-high-frequency "reshare to your top contacts" slots (e.g. iMessage's top-contacts row), not a general detail-page action row.

### Recommendation (concrete, element-by-element)

- **Remove** the explicit "Dismiss" `OutlinedButton`. Drag handle + scrim-tap + swipe-down remain, all already TalkBack-accessible per the source evidence above — zero a11y cost. — ✅ IMPLEMENTED (Commit 1).
- **Fix Share's dark-theme contrast** (Part 1 row 7) now that it's the sheet's only primary-row button — either a visible border/elevation on the fixed `Ink`/`Canvas` pair, or switch it to read off `colorScheme.primary` directly. — ✅ IMPLEMENTED (Commit 1): switched to `colorScheme.primary`/`onPrimary`.
- **Demote the quick-share row visually**: change `WhatsApp`/`X`/`Threads` from full-width `OutlinedButton`s (Dismiss's old visual weight) to small, icon-only chips/`FilledTonalIconButton`s, so the sheet's grammar reads as "one primary Share action + small shortcut icons," never "a row of look-alike buttons." Keep the existing installed-app-check/omit-not-grey logic (`visibleShareTargets`) unchanged — this is a visual-treatment change, not a logic change. — ✅ IMPLEMENTED (Commit 1): `FilledTonalIconButton`s, 48dp, single-letter monogram (no icon-library dependency), `visibleShareTargets` untouched.
- **Add `Modifier.verticalScroll(rememberScrollState())`** (or migrate to `LazyColumn`) to the root `Column` — independent of the above, and the single highest-severity item in this section since it's a reachability bug already provably reproducible from a real device capture. — ✅ IMPLEMENTED (Commit 1).

**The `reducedMotion` convention itself is genuinely solid** — `LocalReducedMotion` (a `staticCompositionLocalOf<Boolean>`) + `systemReducedMotion()` expect/actual (Android: `ANIMATOR_DURATION_SCALE == 0`; jvm/wasmJs: always `false`), threaded explicitly into `core:ui` composables as plain `Boolean` params for module-boundary reasons documented in-line. Every animated element above respects it — **except** the Onboarding pager, a real, small, fixable gap in an otherwise-consistent pattern.

### Research: Material 3 motion + calm-app restraint

`m3.material.io`'s motion pages render empty via both `WebFetch` and the Browser pane (a client-rendered SPA; the Browser pane additionally reports the whole `m3.material.io` origin as **policy-blocked**) — see Sources for the honest failure record. In place of the marketing page, the actual token values were pulled directly from this project's real dependency, which is more precise anyway for a Compose-specific recommendation:

- **Duration tokens** (`androidx/compose/material3/tokens/MotionTokens.kt`, from the real `material3:1.8.2` sources jar): `Short1..4` = 50/100/150/200ms · `Medium1..4` = 250/300/350/400ms · `Long1..4` = 450/500/550/600ms · `ExtraLong1..4` = 700/800/900/1000ms.
- **Easing curves** (same file): `Emphasized` = `cubic-bezier(0.2, 0, 0, 1)` · `EmphasizedAccelerate` = `cubic-bezier(0.3, 0, 0.8, 0.15)` · `EmphasizedDecelerate` = `cubic-bezier(0.05, 0.7, 0.1, 1)` · `Standard` = `cubic-bezier(0.2, 0, 0, 1)` · `StandardAccelerate` / `StandardDecelerate` also present.
- **Spring presets** (`androidx/compose/animation/core/VectorizedAnimationSpec.kt`, from the real `animation-core:1.9.0` sources jar): `DampingRatioNoBouncy = 1.0f` (critically damped, **zero** overshoot) · `LowBouncy = 0.75f` · `MediumBouncy = 0.5f` (**TerraWatch's current choice for all 3 signature springs**) · `HighBouncy = 0.2f` (max overshoot). `StiffnessMedium = 1500f` is the paired default.
- TerraWatch's resolved Compose Multiplatform version (1.8.2) **does not yet include** M3 Expressive's newer `MotionScheme` spring-token API (confirmed absent from the jar's file listing) — today's bounce is a hand-picked Compose-foundation preset, not an "M3 Expressive spec," which matters for how confidently this can be called a brand-identity choice vs. an accident of which preset was nearest to hand.
- **Calm-restraint principle** (UXmatters, "Designing Calm: UX Principles for Reducing Users' Anxiety," fetched in full): *"animations should always serve a purpose — such as indicating a progression, confirming an action, or guiding attention — not just add visual flair"*; *"restraint is not omission — it's care."* Directly applicable to an earthquake app: motion on the magnitude/severity path specifically should never read as celebratory.
