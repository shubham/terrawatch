Plan 4 Task 4 fix round -- foldable posture display-size dump
================================================================

Purpose: task4-foldable-posture-closed.png and task4-foldable-posture-reopened.png
(captured during the original Task 4 session) are byte-identical (same MD5,
dbc1f4bcaf06877b341d0fede4117da9). The original report already reasoned this was an
AVD-profile characteristic, not a capture mistake ("this particular AVD profile
doesn't change the reported display size on a bare posture change (no separate
cover-screen resolution), so the layout itself doesn't change either"), but that
reasoning was asserted, not measured. This dump measures it directly: cycles the
same three postures through the emulator console and captures the actual system
display metrics at each one, rather than relying on screenshots alone (which can
only ever look identical if the underlying metrics are identical -- they cannot by
themselves distinguish "no-op" from "capture bug").

Device: pml_fold36 (Generic 7.6in Foldable AVD, API 36), booted headless
(-no-window -no-audio -no-boot-anim), adb serial emulator-5554.
Config (~/.android/avd/pml_fold36.avd/config.ini): single fixed hw.lcd.width=1768,
hw.lcd.height=2208, hw.lcd.density=420 -- no separate cover-screen resolution is
configured for this profile at all, which is the root cause the dump below confirms.

Method: authenticated to the emulator console (port 5554, token from
~/.emulator_console_auth_token) and sent `posture <n>` for each of this AVD's three
configured postures (hw.sensor.posture_list=1,2,3 / hw.sensor.hinge_angles_posture_
definitions=0-30, 30-150, 150-180 in config.ini), waiting 2s after each for the
framework to settle, then ran `adb shell wm size`, `adb shell wm density`, and
`adb shell dumpsys display` (DisplayDeviceInfo line only, reproduced in full below).

The three DisplayDeviceInfo records above are identical byte-for-byte apart from the
"posture N" label used to select which command preceded each capture -- same
uniqueId, same resolution, same density, same rotation, same everything.

Conclusion: `wm size`, `wm density`, and the full `dumpsys display` DisplayDeviceInfo
record (same uniqueId, same 1768x2208, same 420dpi, same rotation 0) are IDENTICAL
across closed/half-opened/opened. This is not a screenshot-capture artifact -- the
system itself reports zero display-metric change across this AVD's posture range,
confirming the original report's reasoning with a measurement rather than an
assumption. task4-foldable-posture-closed.png/reopened.png being byte-identical is
therefore expected and correct, not a gap: there is no distinguishing screenshot to
take on this AVD profile, because the OS-level input this app's layoutMode() keys
off (WindowSizeClass, itself derived from actual display width/height) never
changes here. A foldable AVD profile with a real distinct cover-screen resolution
would be needed to exercise a genuine posture-driven layout change; none was
available in this pass.
